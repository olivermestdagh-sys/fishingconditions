# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Full feature list, architecture diagram, tide-condition rules and privacy model are in `README.md` — read that first. This file only adds what a session needs to actually *work* in the repo: commands, the parts of the architecture that span multiple files, and two standing process rules.

## Commands

- `npm test` (= `node --test`) — runs everything in `tests/*.test.mjs`. Run a single file directly: `node --test tests/tide.test.mjs`.
- `npm run check-pages` (= `node scripts/check-page-scripts.mjs`) — verifies every HTML page loads every shared `js/*.js` file it actually uses, in the right order. **Run this after adding/removing a function in a shared `js/*.js` file, or adding a `<script>` tag to any page** — it's the one check that catches a function only existing on some pages (see Architecture below).
- Syntax-check a script: `node --check some-file.js`. `user-backend.js` is ESM despite the `.js` extension — copy it to a `.mjs` path first (`cp user-backend.js /tmp/user-backend.mjs && node --check /tmp/user-backend.mjs`), exactly as CI does.
- `python -m py_compile scripts/fetch_conditions.py scripts/observation_archive.py` — compile-check the data pipeline (no Python test runner here).
- No frontend build step — plain HTML/CSS/JS, no bundler, no `npm run dev`. Just edit and reload.
- Deploy: pushing to `main` deploys the static site (GitHub Pages) automatically, and also auto-deploys the `fishingconditions-users` worker via `.github/workflows/deploy-worker.yml` *if* `user-backend.js` or `wrangler.toml` changed and the `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` repo secrets are set. Manual worker deploy (e.g. to test before pushing): `npx wrangler deploy`.
- CI (`.github/workflows/ci.yml`) runs all of the above (syntax check, check-pages, tests, Python compile-check) on every push/PR — run them locally first rather than finding out from a red CI run.

## Architecture

- **Two independent Cloudflare Workers**, deliberately separate (different secrets, different blast radius — see `user-backend.js`'s own header comment): `user-backend.js` (accounts, sessions, D1, marks, per-user prefs — the real backend, config in `wrangler.toml`) and `willyweather-search.js` (a tiny stateless proxy that only exists to keep the WillyWeather API key out of the browser).
- **Frontend has one shared global scope, not modules.** The shared code was originally one 9,600-line `charts.js`; it's since been split into `js/*.js` by topic (chart drawing, maps, marks, tide logic, backend helpers, prefs sync, etc.), but every one of those files still shares a single global scope — no `import`/`export`, no bundler. Each page (`index.html`, `conditions.html`, `reports.html`, `locations.html`) loads only the shared files it needs via plain `<script>` tags, in a specific order, then its own page script (`week.js`, `app.js`/`map-live.js`/`sync.js`, `reports.js`, `locationsadmin.js`). `scripts/check-page-scripts.mjs` is what keeps this honest — see Commands above. `live.html`/`sync.html` are just redirects into `conditions.html`'s Live/Import modes now.
- **conditions.html is three modes on one map**: Normal (tracked spots + marks), Live (GPS, nearest spot, tap-to-log; `map-live.js`), Import (review a Garmin/Lowrance export; `sync.js`).
- **Live config vs. batch data**: WillyWeather-derived numbers (forecasts, scores) only update on the 3-hourly GitHub Actions pipeline (`update.yml` → `scripts/fetch_conditions.py` → commits `data/conditions.json` + `config/locations.json` straight to `main` — a force-push can race with it). Everything else about a location (display name, group, timings, tide offset) is read live from D1 via `/api/public/locations` at page load and merged in (`mergeLiveLocationConfig`, `js/chart-render.js`) — a Settings edit shows up immediately, without waiting for the pipeline.
- **Privacy model**: anonymous visitors get conditions + the tracked-location list only. Marks and personal settings (home location, Google Routes key) require sign-in and are scoped to that user (D1 `fishingconditions-users`, schema in `schema-v2.sql`). Every state-changing request must come from the site's own origin (CSRF guard in `user-backend.js`); the pipeline instead authenticates with a shared-secret header.
- **Tide condition/extreme classification** (`classifyTideFromExtrema` in `js/marks-core.js`; `rankExtremum` + `naiveDateOnlyStr` live in `js/chart-base.js` so Week Ahead can use them) is shared by every mark-creation path — Live quick marks, a map click, and the Sync import — touching this logic means checking all three call sites, not just one.
- **Trough widening** (`applyTroughWideningToRows`, `js/chart-render.js`; spec `docs/lang-lang-trough-widening-spec.md`): the synthetic tide curve is too fast through a shallow low, so per-location `locations.hlw_offset`/`llw_offset` (minutes; plus `hhw_offset`/`lhw_offset` for highs, per `docs/lang-lang-trough-widening-spec V2.md`) re-time the curve around each tide extremum (each affected high-low-high leg is redrawn as one smooth monotone cubic Hermite through extremum / crossing / extremum, slope 0 at the extrema), run after `applyTideOffsetToRows` in `renderConditionsChart` (`troughOffsets` option, passed by week.js/app.js/map-live.js). It anchors on the `minTideHeight` crossings: for a low, the falling crossing moves earlier and the rising one later by O, and the low itself O later (exactly the spec's numbers; only the curve BETWEEN those points is smoothed, and the exact extremum/crossing times are handed to `findTideExtrema`/`findTideThresholdCrossings` via `rows.widened` so labels/dots show them rather than hourly-sampled estimates); for a high, the crossing into it moves earlier and the one out of it later (plateau widening) but the high itself does not move. Each leg's crossing is owned by the low if `minTideHeight` is at/below the leg's height-midpoint, else by the high; shifts are capped at half the leg. Only existing crossings move, so a near-miss day (curve never crosses) is NOT fixed (spec's open "height margin" idea). Client-side only (the pipeline just passes the fields through `export_locations_json`); edited in the Map's location editor (Tides group); manual `ALTER TABLE` on D1 done 2026-10-05, Lang Lang `hlw_offset` = 40. Marks' tide classification (`js/mark-lookup.js`) does not see the widening.
- **Per-user synced settings** (`js/prefs.js`, `Prefs.set`/`Prefs.remove`, each page's `await Prefs.load()` at init, backed by D1 `user_prefs` via `/api/prefs`): the allowlist of which localStorage keys sync (`SYNCED_PREF_KEYS`) is duplicated in `user-backend.js` and `js/prefs.js`, and a test checks they match — update both when adding a new synced preference.
- **Trip Defaults** (Map, Normal mode, signed-in only; `js/trip-defaults.js`, opened from `openTripDefaults` in `map-live.js`): a full-screen hub reusing the `.live-card-*` CSS to manage Trips (`user_trip_setups`) -> Actions (`user_trip_actions`, `/api/tripactions`, added to `schema-v2.sql` and needing a manual `CREATE TABLE` on D1) -> Rod Setups (`/api/rodsetups`). This is now the ONLY place Trips/Actions/Rod Setups are managed — Settings has no Trips section any more (the worker routes stay). In Live mode (`map-live.js`, "Live trips" section) Start Trip picks a trip and shows its Actions as toolbar buttons: tapping one ends any running session and starts a Session Start mark built by `buildSessionStartFromAction` (Action species/method/berley/bait + its Rod Setups' rod/rig and the new `marks.rigOptions` field for rig sub-list items); tapping the running one ends it; End Trip clears it. The old Session defaults / + Session / End Session-Move toolbar buttons are gone (trips replace them; `liveSessionDefaults` still feeds +Catch); +Catch while an Action is running takes everything from that Action (species cards: its targets, the trip's other targets, then the rest; berley/method/bait; the Rod Setup, asked only if there are several) and always has a water-depth card; the LAST card is Bait (the Action's bait first, then every other bait; optional — unanswered keeps the Action's bait; `buildCatchCardSteps`/`buildCatchFromCards` take it, map-live.js puts the answer on after the Action's gear); two device-local buttons, Water (cycles the Water Condition list) and Depth (stepper), set `liveMarkDefaults` used for trip Session Starts, +Catch and the You-are-here quick mark. The active button is derived from `liveActiveSession()`, not stored. Actions used to carry a `bait` list (`user_trip_actions.bait`). **Rod positions** (2026-10-05): an Action's Rod Setup pills each carry a 2x2 grid of regions (the Action's four rod positions, `user_trip_actions.rod_slots`, manual `ALTER TABLE` done on D1); tapping a free region takes it (green), a setup holds ONE region (taking another moves it), a region another setup holds is greyed, your own region toggles off (`tdRodSlots`/`tdToggleRodSlot`; API `rodSlots`). `rod_setup_ids` stays the list everything else reads (written in slot order); `tripActionRodSlots` only trusts `rod_slots` while it names the same setups as the list, so controller edits to the list can't leave stale positions. Max 4 setups per Action in the editor. The controller reads them as `rodSlots` on each config action and moves/swaps rod setups with `action_update` `{actionId, rodSlots:[4 ids|null]}` (also rewrites `rod_setup_ids`). During a trip each Action pill has a gear that opens Trip Defaults straight on that Action in quick-edit mode (`start` option of `showTripDefaults`): its active choices show as summary chips at the top and tapping one opens just that category's options. **Rod Setup bait** (2026-10-05): a Rod Setup also has a multi-select `bait` list (`user_rod_setups.bait`, JSON; manual `ALTER TABLE` on D1 done 2026-10-05), picked on the Rod Setup screen. Marks combine it with the Action's bait (Action's first, then the setups', no duplicates): Session Start (all the Action's setups), Catch (the chosen setup), and the Live Bait card's preferred list; worker twins `ctlBuildSessionStart`/`ctlCatchFieldsFromAction`, and the controller config + `rodsetup_update` carry `bait`. **Bait sub lists / Bait Options** (2026-10-05): Bait values can have a Sub List like Rigs (`SUBLIST_FIELDS` in user-backend.js; same `has_sublist`/`sub_list`/`option_images` columns, private overrides and option pictures, the Settings editor in locationsadmin.js is shared and carries `data-field`). Picked options are the new mark field `baitOptions` (`marks.bait_options`, comma-joined, twin of `rigOptions`: edit form row that follows the Bait pills via `refreshSublistOptionsControls`, view popup, filter, Session End carried field) and `bait_options` on rod setups AND trip actions (`baitOptions`, picked in Trip Defaults under Bait; a bait change prunes options that no longer belong). **Bait now lives ONLY on Rod Setups (2026-10-05): Actions no longer have a Bait / Bait options UI, the builders ignore `user_trip_actions.bait`/`bait_options` (columns and old data left in place), `action_update` no longer takes bait, and the controller config's actions carry no bait.** Builders take the setups' bait/options (Session Start: all the Action's setups; Catch: the chosen setup, so several setups and none chosen = no bait) (browser + worker twins, parity-tested); a Live/controller Catch with a Bait answer keeps them only when that bait is one of the configured ones. Controller: config has `baitLists` ([{name, options, optionImages}]) and `bait`/`baitOptions` on setups; `action_update`/`rodsetup_update`/`mark_update` accept `baitOptions` (validated against the chosen baits' sub lists; changing bait clears/prunes). Manual `ALTER TABLE ... ADD COLUMN bait_options TEXT` on `marks`, `user_rod_setups`, `user_trip_actions` done on D1 2026-10-05. "Restore missing values" does NOT cover bait options yet. The Live +Catch flow has a multi-select **Bait options** card after Bait (`baitSublists` in `sessionCardOptions`, `defaults.baitOptionsFor` = Action + chosen Rod Setup options as the starting selection; `answers.baitOptions` wins on save; a different Bait answer resets it); the controller `catch` event may carry `baitOptions` (array) likewise. Only `conditions.html` loads it.
- **Mark edit form** (`buildMarkPopupEditHtml`, `js/marks-core.js`): order is Name, Type, Species, Size, Gear/Setup (bait, rig, rig options, rod, berley, method), Weather, Date/Time, GPS (DD always showing; DMS/DDM in the box), Owner, Notes. Rig options are the chosen Rig's Sub List (`rigSublistMapFor`, plus your `rigSublistOverridesMap` from `js/backend.js`) and follow the rig live (`refreshRigOptionsControls`, run from `syncMarkFormPills`).
- **Mark List pictures** (`js/species-image.js`, `handleMarkListImages`/`handleRigOptionImages` in `user-backend.js`, `imageHolder`/`openImageViewer` in `locationsadmin.js`): Species, Bait, Rig, Rod, Berley and Fishing Method values carry up to 12 pictures each (`species_images` bytes + `user_mark_lists.image_index`). A Rig's sub-list OPTIONS have no rows of their own, so their pictures are indexed per option in `option_images` (JSON `{option: [{id,v}]}`) on the rig row, or on your private override (`user_rig_sublist_overrides.option_images`, route `?scope=private`); removing an option/override deletes its pictures. Species keep the Live Catch "Select by image" gallery; the others show their first picture beside the button on the Live/Trip pick cards (`thumbsFromMarkLists`, `rigOptionThumbs`, `stepThumbs` in `js/live-cards.js`, `choice()` in `js/trip-defaults.js`). `option_images` columns needed a manual `ALTER TABLE` on D1 (done 2026-10-01). Removing a list value or rig option in Settings asks first (`confirmRemoveListItem`: its pictures and how many marks use it), and the Mark Lists editor has "Restore missing values" (`findMissingListValues`): it re-adds names your marks use that are no longer in the lists (names only — colour is new, pictures/limits are not recovered).
- **Fishing Controller** (design brief: `docs/Fishing Controller Design Brief.md`; the brief predates the site, so where they differ THE SITE WINS): a handheld ESP32 controller <-BLE-> an Android app (separate repo `OneDrive\Fishing\fishing-controller`, local only for now; fake-controller phone app built, Bluetooth link waits for the hardware) <-HTTPS-> `/api/controller/*` in `user-backend.js` (section "Fishing Controller API"). It adds no data model: controller events become the same marks the Live page makes. `trip_start`/`trip_end`/`action_start`/`action_end`/`catch` -> Session Start/End and Catch marks via server copies of the browser builders (`ctlBuildSessionStart`/`ctlBuildSessionEnd`/`ctlBuildCatch`/`ctlNextSessionNumber`; `tests/controller-parity.test.mjs` runs them against `js/trip-defaults.js`/`js/live-cards.js`/`js/catch-limits.js`, so change both together). Events are idempotent: `controller_events(user_id, device_id, seq)` is written in the same D1 batch as the marks (`source: "Controller"`, `source_uuid: fc:<device>:<seq>[:start|:end]`). The running trip/action is the synced pref `liveActiveTrip` (`{tripId, actionId, sessionGroupId}`, `{"tripId":null}` = none — a value, never a removal), which Live mode re-reads on focus/every minute (`liveSyncFromAccount`, `map-live.js`, with `GET /api/public/marks?since=<ms>` for marks made elsewhere). Auth is a per-user device token (`Bearer fc_…`, only a sha-256 hash in `controller_tokens`, created/revoked in Settings > Fishing Controller), accepted ONLY on `/api/controller/*` and exempt from the Origin/CSRF guard there. The Worker saves marks WITHOUT tide/weather; the browser completes them on load (`enrichControllerMarks`, `js/mark-lookup.js`). `controller_tokens`/`controller_events` needed a manual `CREATE TABLE` on D1 (done 2026-10-02), `controller_track` likewise (2026-10-03). The phone also uploads its GPS track (`POST /api/controller/track`, idempotent on user+device+ts, device token; `GET` reads it back for a signed-in visitor). Query budget: the free Cloudflare plan allows ~50 D1 queries per request, so an events request stops after `CTL_QUERY_BUDGET` prepared statements and answers the remaining events `deferred` (the app leaves those pending and resends) — keep the per-event query count low when changing `ctlProcessEvent`. Times: the controller sends UTC epoch seconds + timezone offset, converted to the site's naive local string (`ctlNaiveFromEpoch`). The controller's "Modify defaults" edits the website's Trip Defaults through two more event types, `action_update` ({actionId, fishingMethod?, berley?, bait?, targets?, rodSetupIds?}) and `rodsetup_update` ({rodSetupId, rod?, rig?, subListItems?}); the Worker only accepts values that already exist in the user's own/Public lists (no creating), rig options must belong to that rig (own Sub List or your private one), changing a rig clears its options like the site, and the config the controller reads carries each action's own choices plus `rods` and `rigs` (`ctlActionUpdateStatements`/`ctlRodSetupUpdateStatements`). The controller also keeps the trip's current Water condition and Depth (always visible at the bottom of its actions screen) and sends them as `water`/`depth` on `action_start`, `action_end`, `trip_end` and `catch`; the Session End takes them from its event (falling back to the Start mark's), so Session Start/End and Catch marks all record the conditions in force at that moment. The pipeline also writes `data/graph/index.json` + one `data/graph/<hash>.json` per location+type (`write_graph_files`, fetch_conditions.py; same numbers as conditions.json, only the fields the controller graph draws, ~50 KB each; failure there never fails the run) so the controller downloads one location, not the 5 MB file. The config also carries `userId` (the controller graph shows Public's saved locations plus that user's own). The config also carries `images` ({Species|Bait|Rig|Rod|Berley|Fishing Method: {value: {id, v}}} — the FIRST picture of each value that has one) and each rig's `optionImages`; the controller app downloads them from the public picture route (`/api/public/species-image/<id>?v=<v>`, no token needed) and shows them full screen as the dial passes over their options. A `catch` event may carry `bait` (a list: the Bait question's answer, `[]` = none) which replaces the action's bait on the mark (`ctlBuildCatch` `bait`; absent keeps the action's). **Trip and Action names** (2026-10-04): marks made on a trip (Session Start/End, Catch — Live page and controller) carry `tripName` / `actionName` as TEXT snapshots (`marks.trip_name` / `action_name`, manual `ALTER TABLE` on D1 done 2026-10-04; not pick-lists, not in `MARK_LIST_FIELDS`, single-valued even on a Session). The Worker builders (`ctlBuildSessionStart`, `ctlCatchFieldsFromAction`, `CTL_SESSION_END_CARRIED_FIELDS`) and the browser twins (`buildSessionStartFromAction` ctx.tripName, `tdCatchFieldsFromAction(…, tripName)`, `SESSION_END_CARRIED_FIELDS`) must change together (parity test). **Default names on a trip** (2026-10-05): Session Start/End are "[Trip] [Action] [Number] Start|End", Catches "[Species] [Trip] [Action] [Number]" (Number = the running session's number; no trip/action name falls back to "Session N Start"/species only). Helpers `tripMarkName`/`tripCatchName` (`js/catch-limits.js`) and `ctlTripMarkName`/`ctlTripCatchName` (worker; parity-tested); `sessionNumberFromName` now reads the trailing "N Start|End" so the next number and the running session still resolve from the name. They are free text in the mark edit form / bulk edit / Copy / filters; the controller can only pick an EXISTING trip or action name (`mark_update`, `null` clears). **Trip log**: `trip_start` puts a `runId` in the `liveActiveTrip` state (kept by `action_start`/`action_end`; a trip started on the site gets one at its first action) and every Controller-made mark is stamped with it in `marks.trip_run_id` (a hidden column, NOT in the site's mark shape; manual `ALTER TABLE` on D1 done 2026-10-04 — the site's `sessionGroupId` can't be used on Catches because the mark editor clears it there). `GET /api/controller/marks[?runId=]` (device token) lists the running trip's marks; the `mark_update` event `{markId, changes:{…}}` (`ctlMarkUpdateStatements`) edits a Controller-made Catch/Session mark from existing list values only — Type, GPS and Source are not editable; changing the rig clears its options; a species change renames a Catch. The config also carries `weatherCondition`/`tideCondition`/`tideExtreme`/`windDirections`. A `catch` event with `tooSmall: true` (the controller's TOO SMALL stop in its size list) has no size, is released and gets the "Too small" note, as on the Live page.
- **Base map toggle** (Map toolbar `#baseMapBtn`, `js/map-core.js` `applyMapBase`/`setMapBase`): OSM raster tiles by default, or the Open Waters Seamap vector chart (`tiles.openwaters.io/seamap/style.json`, CC BY 4.0, not for navigation) via MapLibre GL JS + `@maplibre/maplibre-gl-leaflet` (`L.maplibreGL`), both loaded from unpkg (SRI) in `conditions.html` only. The choice is per-device (`goodConditionsMapBase`, NOT synced); the button is hidden and OSM used if WebGL/the plugin is unavailable. The map is rebuilt on every `renderLeafletLocationMap`, which re-applies the saved base and rebinds the button.
- **Facet filters** (Week Ahead's Type/Location Group/Shore Direction/Locations, `js/week-tools.js`) are 3-state (`{include, exclude}` Sets per value) and cross-narrow each other's candidate lists — the same convention as the Map's own mark filters (`js/marks-tools.js`).

- **Trip log** (2026-10-05; `trip_log` + `trip_log_rods` in `schema-v2.sql`, manual `CREATE TABLE` on D1 done 2026-10-05; Worker section "Trip log" in `user-backend.js`, site side `js/trip-log.js`, only `conditions.html` loads it): an append-only record of everything done on a trip run, for later reports (e.g. hours fished with a bait; none are built yet), written IN ADDITION to the marks. One `trip_log` row per event (`trip_start | trip_end | action_start | action_end | change | catch`, grouped by `run_id` = `liveActiveTrip.runId`), names as text snapshots, `lat`/`lng` nullable, `mark_id` linking the Session/Catch mark, weather/tide columns NULL until backfilled. **Reporting rule**: a state (action, rod setups, water, depth) lasts from its row until the next row of the run, so `action_start` and every `change` row carry the FULL state (`trip_log_rods` = one row per rod setup in force, JSON-array bait/rig-options columns for `json_each`; a `catch` row carries just the setup used); `action_end` is only time/place; a new `action_start` implicitly ends the previous action. Idempotent: row id = `tl_<user>_<source_uuid>`, `INSERT OR IGNORE`. Controller path: `ctlProcessEvent` calls `tlogStatements` in the same batch as the marks (trip_start/trip_end/action_start/action_end/catch, `action_update`/`rodsetup_update` while that action runs = `change`; Water/Depth arrive on events, so a catch whose water/depth differs from the last logged is also a `change` — found with `lastCond`); this costs a few extra queries per event, which is why the events test sends 2-3 events per request. Site path: `logTripEvent` (queued in localStorage `tripLogQueue`, flushed by `POST /api/triplog`, retried from `liveSyncFromAccount`, never blocks a mark) from `map-live.js` (Start/End Trip, action pills, Water/Depth buttons, +Catch) and from `put()` in `js/trip-defaults.js` (editing the running Action/Rod Setup). The browser's `tripLogRodRows` and the Worker's `tlogRodRows` are twins (`tests/trip-log.test.mjs` compares them). Backfill: `enrichTripLog` (run from `liveSyncFromAccount`) takes `GET /api/triplog?needsConditions=1` rows (older than 20 min; a row with no position borrows the nearest same-run row's), runs `fillBlankMarkConditions`, and `PATCH /api/triplog/<id>`; `conditions_at` is set even if nothing came back. A Session/Catch mark with a `tripName` has a "Trip log" button in its popup (`showTripLog`, `GET /api/triplog?markId=`).

## Keep this file updated

Treat this file as living documentation, not a one-time snapshot. When a change you make shifts something described above — a new shared `js/*.js` file, a changed/added command, a new worker, a new cross-cutting pattern, a renamed file this doc points at — update the relevant section in the same session, before moving on. A future session trusts this file to be current; let it go stale and it actively misleads instead of helping.

## Always commit and push

This is a solo project on a public repo with automatic deploy on push (GitHub Pages for the site, GitHub Actions for the worker — see Commands). After finishing and verifying a change, commit and push to `main` immediately, without asking first — then report what you did (with any caveats on what you couldn't test). Don't end a turn with "commit and push?"; just do it. If the push is rejected because the scheduled "Update conditions data" commit landed first, `git fetch` + `git rebase origin/main` (data-only commits, safe to rebase past), then push again.

Still ask first for anything genuinely risky or destructive: history rewrites, force-push, deleting data, touching secrets, or anything outside this repo.
